# Playtest night — 2026-09-18

**Subject**: drafting (`mtg-draft-runner`), chosen from the ledger rather than
from memory. Deriving the per-subject last nights out of
`reports/playtests/LEDGER.md` gave the GUI (G) 09-17, the CLI (V/M) 09-16, the
game (C/L) 09-15, the harness (H) 09-14 and drafting (D) 09-13 — so drafting
had gone longest without a night, by a day over the harness. Reading the ids
actually run out of the ledger (`D1`–`D11`) against the ids in
`docs/playtest/drafting.md` left **D12–D20 untried**; three of them were taken.

**Crew**: 3 probes. **D15** run here; **D17** and **D12** run in parallel as
subagents, each with its own capture directory under `logs/playtest/`.

**Runs**: ~30 `mtg-draft-runner` runs — 7 deck-answer shapes for D15, 7 failure
scenarios for D17, 5 seeded pairs plus a `--save` pair for D12 — and several
thousand captured stub invocations. **No metered API seat was spawned at any
point**: every run passed `--model cc` explicitly (the flag defaults to
`claude`), and every run drove a `CLAUDE_CODE_BIN` stub, so not one real model
call was made all night.

**Issues**: 8 filed — #535–#542.

The night's shape: **the draft runner is careful about the answers it expects
and careless about everything around them.** All three probes started from a
different question and landed on the same class of defect — the program has a
well-tended happy path, and the paths out of it (a malformed answer, a fatal, a
second run of the same seed) were each written once and never exercised. The
deck parser allocates on a number it has not checked (#535) and silently
rewrites the ones it cannot read (#536). The fatal exit skips every destructor,
so it orphans the other seats' `claude -p` trees to init (#537) — and the
signal handler that was supposed to be the safety net has four slots against a
default of eight seats (#538). And the one seeded property the runner advertises
turns out to hold for the *run* and not for the *log* (#541).

Two things were checked and deliberately **not** filed, because the code says
they are intended: the `debug_assert!` schema-key guards in both request paths
compile out of release, but the comment at `mtg-player/src/llm.rs:2724` says so
on purpose ("fail loudly where a developer will see it, and let a live game take
the retry path rather than crash mid-tournament"); and `--log` opens
`append(true)` (`game_log.rs:65`), so re-running with the same path concatenates
runs — each run writes its own `HEADER`, so a reader can still split them.

## D15 — the deck answer the schema cannot describe

**Result: the maindeck is the one number in the program with no bound on it,
and the numbers it cannot read are rewritten to zero without a word.**

Seven deck-answer shapes, `--set isd --players 2 --best-of 1 --model cc
--seed 7`, each through a `CLAUDE_CODE_BIN` stub:

| shape | what the runner did | verdict |
|---|---|---|
| `maindeck {card: 4e9}` | **SIGABRT, exit 134**, allocator backtrace, log stops at the `DECK BUILDING` banner | **#535** |
| `maindeck {card: 1e6}` | refused, 10 retries, fallback deck | ok — but the message understates |
| `maindeck {card: 1.0}` | **accepted, 0 retries**, the card lands in the *sideboard* | **#536** |
| `maindeck {card: "1"}` and `{count: 1}` | **accepted, 0 retries**, 2 cards dropped | **#536** |
| `lands {Island: -5}` | **accepted, 0 retries**, land silently dropped | **#536** |
| `lands {Island: 1e12}` | refused: `count is 4294967295 — that's clearly a hallucinated number` | ok — but quotes the clamp |
| non-schema keys (`deck` / `basics`) | refused: `missing "maindeck"`, 10 retries, fallback | **PASS** |

`parse_deck_response` expands `{name: count}` into a `Vec<String>` of `count`
clones *before* returning, and `validate_deck` — the thing that would reject the
count — never runs. The 200-card hallucination guard that exists covers `lands`
only, which is why a land count of 1e12 is caught and a maindeck count of 4e9
takes the process down. `u32::MAX` slots of `String` is ~103 GB for the Vec's
backing store alone; the allocation cannot succeed on any machine. The cost
lands at the last step, after every pick has been paid for.

The second half is quieter and probably worse. `as_u64()` returns `None` for
`1.0`, `"1"`, `{...}` and `-5`; in the maindeck branch that becomes `0` via
`unwrap_or(0)` and the card vanishes, in the lands branch the entry is skipped.
Either way the answer is rewritten and then judged as if the seat had sent the
rewritten version: `DECK_RESPONSE attempt 1/1 (accepted)`, `DECK (40 cards, 0
retries)`, and the card the seat maindecked sitting in its sideboard. Unlike
#195 and #200 there is no counter, no `WARN` and no `FALLBACK` marker, because
from the runner's point of view nothing went wrong.

**The cross-surface check the README asks for** turned this from a report into
an argument. `parse_pick_response`, in the same crate, takes the *identical*
malformed input and handles it safely and loudly — `?` out instead of
`unwrap_or(0)`, the index range-checked against the pack, and the fall-through
ending at `Pick::Substituted` with a `WARN`, a log line and a per-seat counter
(#195). So the deck path's silence is not a house style; it is the one place the
house style was not applied. Posted as a comment on #536 so the fixer has the
shape to mirror. Going the other way, `deckbuilding.rs:236` is the **only**
model-number-driven allocation in the three crates — the game harness takes
indices from a seat and never a count — so #535 has no twin on the other
surfaces.

## D17 — which seat the fatal blames, and whether one seat can block the report

**Result: the blame is survivable, the cleanup is not. The fatal exit sweeps
nothing, and #206's signal handler was sized for a two-seat game.**

The idea's own two claims came back mixed, and the honest answer is that the
reading behind them was half wrong. `enumerate()`'s index *does* equal the seat,
because `pick_inputs` is built `(0..args.players)` in order, so a lone seat-3
failure reports `seat 3` correctly — the indexing bug does not exist. What does
exist is first-`Err`-wins in seat order: with seat 3 failing hard at t≈0.2s and
seat 0 merely timing out later, the headline blames **seat 0** and seat 3 is
never named, while `API_FATAL`/`API_ERROR` carry a thread id (`t5`) and no seat
at all. Nor does a hang block forever — the per-call watchdog and the retry
budget bound every call — but the report waits on every lower-numbered seat, so
a run that was dead at t≈2.4s printed nothing until t=45s, and with shipped
defaults that is up to ~600s showing only `Pack 1 Pick 1/14` (#539).

The finding that matters was not in the idea. `report_worker_failure` → `die` →
`std::process::exit(1)` runs no destructors and raises no signal, so nothing
sweeps `LIVE_GROUPS`: with seat 0 failing while seat 3 is still in flight, the
runner exits and seat 3's wrapper survives at `PPID=1` with its grandchild
still running, five seconds after the runner is gone (#537). The deck-build
scope behaves identically. On a metered seat that is a live call nobody is
waiting for any more.

And the safety net has a hole in it that predates all of this. `LIVE_GROUPS` is
a fixed array of **four** `AtomicI32` slots, with a comment reading "Four slots
is more seats than a run has" — written for `mtg-runner`, where a game has two
seats. `mtg-draft-runner`'s `--players` **defaults to 8**. Verified
independently from the source and by observation: eight seats in flight,
`kill -TERM`, four killed and four orphaned to init. At `--players 4` all four
die correctly, which is exactly why #206 has looked fixed ever since (#538).

A fourth issue came out of the setup rather than the probe, and both subagents
hit it independently: a **relative** `CLAUDE_CODE_BIN` passes
`claude_code_available()`, which runs in the invocation cwd, and then fails
every single call, which runs in the seat's scratch `current_dir` — so the guard
that exists to "refuse before anything is spent" passes, and the run burns its
whole wall-clock retry budget on `os error 2` (#540).

## D12 — seeded-run identity beyond the packs

**Result: #402's fix holds end to end. The run replays; the log does not.**

Five seeded pairs (`--players 2 --best-of 3` at seeds 41/7/99, `--players 4
--best-of 1` at seed 41, twice) under a stub that is a pure function of
(`--json-schema` argv, prompt) — no counters, no clock, no `$RANDOM` — selecting
by SHA-256 over the schema it is handed rather than by pattern-matching prompt
text, so the tournament half was answered *validly* (no "answers rejected" line)
rather than fed a constant.

`to_decklist`'s #402 hole is fixed, and verified end to end rather than by
reading its comment: same packs, same picks, same pools, same decks in library
order, same opening hands, same mulligans, same 352 game decisions, same match
score, same standings, same usage block. Every one of the four ordering surfaces
D12 named is deterministic, and one of them for a reason worth writing down —
`Cargo.lock` shows `serde_json 1.0.149` with no `indexmap` dependency, so
`preserve_order` is **off** and `serde_json::Map` is a `BTreeMap`. That makes
`deck_schema_for`'s explicit sort redundant, every other map in both request
paths deterministic for free, and `parse_deck_response`'s expansion order
lexical — all of which silently changes if anyone ever turns that feature on.
(Verified here independently of the probe.)

The prompts hold too, which is the strongest single result of the night: 440
stub invocations per run at `--players 2` and 818 at `--players 4`, multiset
diff empty both ways, and matching the per-`--session-id` streams pairwise, every
stream byte-identical. Each seat was asked the same things in the same order.

What does not reproduce is the log file, and only from `DECK BUILDING` onward.
`log_deck_building!` is called from inside `s.spawn`, and the tournament's
`PROMPT`/`RESPONSE`/`CONCEDE-CHECK` records are written inline from each match
thread, so concurrent workers merge into the log in scheduler order. Same lines,
different order — `diff` gives up to 1,047 hunks at `--players 4` while
`diff <(sort a) <(sort b)` is empty every time (#541). The pick loop does the
opposite, joining in seat order and logging afterwards, which is why the whole
draft half is byte-identical.

Two methodological notes that cost the probe real time and are now in the guide.
`--players 2 --seed 41` diffs to **zero** lines — it is a two-way race that fell
the same way twice — while three of the other four pairs failed, so a
determinism claim here needs at least three seeds and one `--players 4`. And
`diff` alone cannot tell "different run" from "same run, different line order";
it has to be paired with the sorted diff.

Finally, the one value that genuinely varies between two identical seeded runs
is recorded nowhere: a 2-seat best-of-3 mints 8 `claude -p` session ids (the
game backend resets per game), and `grep` finds none of them in the `--log` or
the `--save` snapshot. `API_ERROR` identifies a call by thread id, which is the
one identifier that means nothing to a reader afterwards (#542). `--save`
snapshots at the same pick count are byte-identical, so #199 still holds.
