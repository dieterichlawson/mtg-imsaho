## G24 — the field that eats the keyboard (#601, #606)

The idea was written from reading `main.ts:313-318`; every part of it is true
at runtime, and it is worse than "some keys are ignored".

`syncField` calls `field.focus()` **on every frame** the widget wants a field
(`main.ts:427`, and `draw()` ends in `syncField()` on a 120 ms interval), and
the window keydown handler opens with `if (ev.target === field) { …Enter,
Escape… return; }`. So at a filtered `list` or a `number`, all seven
documented keys land in the box as characters:

```
===== choose-card-name =====
before:   {"mode":"list","logOpen":false,"overlay":null,"stopAtPass":false,"query":"","focused":true}
key 'l' -> {"mode":"list","logOpen":false,"overlay":null,"stopAtPass":false,"query":"l","focused":true}
…
key 'f' -> {"mode":"list","logOpen":false,"overlay":null,"stopAtPass":false,"query":"lgGedsf","focused":true}
Escape -> {"mode":"list","logOpen":false,"overlay":null,"stopAtPass":false,"query":"lgGedsf","focused":true}
```

Three things in that capture are each worth a line. The overlays, the log and
both toggles never move. **Escape is not an escape** — it blurs, and the next
frame focuses the field again, so `focused` is still `true` after it and the
typed text is still there. And the seven keystrokes have filtered the prompt
to `NO MATCHES MATCHING "LGGEDSF" (OF 7)`, an empty row list over a question
you still have to answer, with no on-screen way back.

The control is what makes it a finding rather than a guess: the same seven
keys at a `mark` prompt, on the same board in the same game, all work —

```
key 'g' -> {"mode":"mark","logOpen":true,"overlay":"graveyard"}
key 'd' -> {"mode":"mark","logOpen":true,"overlay":"library"}
key 's' -> {"mode":"mark", …,"stopAtPass":true,"notice":"Stopping at every priority."}
key 'f' -> {"mode":"mark", …,"notice":"Auto-pass passes priority, and this is not a pass."}
```

— and note the last line. At a widget with no field, `f` at a non-pass prompt
*says* why it did nothing. At the two widgets with a field, nothing is said,
by any key, ever.

That last observation is #606, filed separately because it is a different
symptom of the same three lines: **#570's fix cannot reach a filtered list.**
`noAnswerHere` lives after the `ev.target === field` early return, so the
sentence it added appears at an unfiltered `list` and never at a filtered one.
Measured both ways, same build:

| prompt | `filter` | Enter | what is said |
|---|---|---|---|
| mulligan (`list`) | false | nothing sent | `Enter does not answer this — click a row.` |
| `ChooseCardName` (`list`) | true | nothing sent | **nothing** |

This also answers G16's open wrinkle — "what Enter does when a `list` has been
filtered to exactly one row". Filtered to exactly one visible row, Enter
sends nothing and says nothing:

```
filtered:    {"query":"Goblin P","visibleRows":1,"notice":null,"sent":5}
after Enter: {"notice":null,"sentCount":5,"stillAsking":true,"mode":"list"}
```

Whether it should *pick* that row is a design question and is left open in the
issue; that it currently does neither is not.

## G17 — the seat that can never give up (#602)

The idea's reading of `gui.rs:190` is right, and the runtime half is worth
having: a `gui` seat holding a decision when its browser is destroyed blocks
for ever and **prints not one byte**.

```
[08:08:13] closing the browser entirely...
[08:08:18] +5s  alive=true ps="Sl         00:05"
…
[08:08:58] +45s alive=true ps="Sl         00:45"
exited: null
reconnect got: {"seq":2,"mode":"menu"} (was {"seq":2,"mode":"menu","ctx":"MAIN PHASE 1"})
```

Two mechanisms, both in `ask`. `said_waiting` latches: the "waiting for a
browser at `<url>`" line fires once at the first decision, *before* anyone has
opened the page, so when the page later closes the one line naming the URL is
never printed again. And it could not detect the close anyway —
`Shared::broadcast` is the only thing that reaps dead clients, and while `ask`
is blocked in `recv()` nothing is broadcast, so `connected()` keeps counting
the closed page.

`Action::AbandonGame` at `gui.rs:212` is unreachable: `Shared` owns the
`Sender` and `GuiPlayer` owns the `Arc<Shared>`, so `recv()` never returns
`Err`. `mtg-runner` has no `--max-actions` and no progress watchdog, so
nothing else can end the game either. G17 asked whether a human seat *should*
wait for ever — on this evidence yes, and the fix is to the silence and the
comment, not to the waiting.

**Checked, correct**: the reconnect promise in `mtg-gui/README.md` holds. A
fresh browser launched 45 s after the first was destroyed is handed back the
same pending decision, `seq 2`, `menu`.

## G22 — the three-badge strip (#603, #604, #605)

The idea predicted that regeneration and attachment fall off the strip first.
What the probe found is both smaller and larger than that.

**Smaller**: the attachment badge is never on the host at all. `permBadges`
draws `→Name` on the *attachment*, so an equipped creature's own strip is
unaffected, and with #525 fixed the inspector does list `1 regeneration
shield` and `Equipped/enchanted with: …`. So the "on no surface of the page"
half of G22 is closed — hovering recovers both.

**Larger**: the strip does not fit the card, at any badge load (#603). `CARD.w`
is 40 and `drawPerm` lays badges out from `x + 3` with no bound, so:

```
+1/1d:   card [5..47] badges ["ATK","+1","1d"]   strip ends 49 overflow +2.0px  neighbour at 48
+10/12d: card [5..47] badges ["ATK","+10","12d"] strip ends 59 overflow +12.0px neighbour at 48
+99/99d: card [5..47] badges ["ATK","+99","99d"] strip ends 61 overflow +14.0px neighbour at 48
```

Cards in a row are at x = 5, 48, 91 — stride 43, width 42 — so there is
**1px of gutter** and the third badge is painted onto the permanent standing
next to it. Three is the cap, so raising the cap is not available as a fix;
the silent `.slice(0, 3)` and the overflow have to be answered together.

**And a fact the idea did not look for**, which turned out to be the night's
best find. `permBadges` marks summoning sickness off the raw view flag. The
engine's flag means "entered this turn" and checks haste separately
(`state.rs:3622`), so a haste creature carries it all turn — and the page
marks an *attacking* Manor Skeleton `z`:

```
hasty attacker: {"id":12,"name":"Manor Skeleton","dmg":0,"shields":0,"counters":{}}
 "badges": [ {"s":"ATK"}, {"s":"z"} ],
 "inspector": { "facts": [ "Color: Black", "Haste", "Attacking Opponent", "Summoning sick" ] }
```

That is #139, closed 2026-09-02. Its fix became `CliPlayer::is_summoning_sick`
and stayed inside `cli.rs`, where the doc comment still says the raw flag is
"misleading on a creature with haste (#139)" and a test asserts it. The page
learned the #221 half (skip non-creatures) and never the #139 half (#604).

Following it onto the other surfaces, as the README asks, found the same hole
in the harness (#605), where it is sharper, because the seat is holding a
legend that contradicts the board:

```
  Manor Skeleton (#3) 1/1 black, haste [S]
…
- `S` = summoning sick (entered this turn, can't attack)
- **haste**: Can attack the turn it enters (ignores summoning sickness).
…
Choose attackers: 0:Manor Skeleton (#3) 1/1 haste
```

The `cc` seat reasoned past it (`My Manor Skeleton has haste and can
attack…`), which is why nobody had noticed, not why it is harmless.

Four surfaces, one flag: CLI right since #139, page wrong, harness wrong,
random seat unaffected (it reads `legal`, not the view's flags).

## Method notes

- 09-22's `fillText` wrapper is still the right instrument, and it now has a
  companion: `window.mtgDebug.inspect(key, kind)` **rebuilds the view index**,
  which a hand-edited view needs before `mtgDebug.render()` will draw it.
  Setting `m.index = undefined` instead throws inside `nameOf`.
- `PermanentView.attacking` is `Option<AttackTarget>`, not a bool. Staging
  `attacking: true` renders but makes `inspectorFacts` throw on
  `'Player' in p.attacking`. Use `{ Player: <opponent id> }`.
- Two haste creatures exist in the pool — **Manor Skeleton** (`{1}{B}` 1/1,
  regenerates) and **Falkenrath Marauders** — and both are in
  `decks/coverage/br-coverage.txt`. A `16 Manor Skeleton / 24 Swamp` deck
  reaches an attacking, summoning-sick-flagged creature on turn 2 of seed 3.
