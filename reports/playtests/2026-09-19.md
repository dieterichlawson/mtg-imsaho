## H16 — the seventeenth prompt (`ChooseDamageEffect`, CR 616.1)

H16 was right that no deck pair in the repo raises it: 12 `random` games of
`ub-zombies` (2 Undead Alchemist) vs `wb-coverage` (Ghostly Possession) raised
it **zero** times. It needs both effects on **one** event and an order that
changes the outcome, and the engine's own model is strict about the second
part — a prevention plus a doubling is *not* asked, because prevention ends
the event in either order. The board that works is **Inquisitor's Flail on an
attacking Undead Alchemist**, damage to a player: `Double` then `Card`, whose
outcomes differ by the amount milled.

Deck that reaches it reliably: `6 Undead Alchemist / 12 Inquisitor's Flail /
22 Island` vs `60 Island`, seeds 7/11/23, with a stub policy that casts the
Alchemist first, then plays lands, then equips. **28 prompts over 5 games**,
2-effect and 3-effect shapes both.

The three verifications the idea asked for:

1. **Each row says what the effect would do** — yes:
   `0: Inquisitor's Flail (#11) on Undead Alchemist (#3): double it to 8` /
   `1: Undead Alchemist (#3): instead p1 mills 4 cards`. The context line
   names the event and the reader (`… would deal 4 combat damage to you`).
2. **The re-raise is not the same row again** — nothing was re-raised, and
   correctly: after `double it to 8` only the Alchemist's replacement is left,
   one effect, so it is applied without asking (`… is doubled to 8` →
   `Undead Alchemist: p1 milled 8 cards`). Two Alchemists on one event are one
   outcome by the engine's model, so that pair is not re-asked either.
3. **The effect the seat picked is the one applied** — 28 of 28, checked
   against the `applies first` log line and the mill that followed.

What broke is the **vocabulary of the rows**, and it is #465 one layer out.
The harness rewrites `p0`/`p1` into you/opp in three places — log entries,
the resolution description, `legal.context` — and the action rows are not one
of them, so `instead p1 mills 4 cards` reaches a seat whose prompt never
defines `p1` and never says which seat it is (0 of 851 prompts contain
`you are p`; the CLI prints exactly that, `you are p1`, which is why the same
label reads fine on a screen). `GAME_RULES` has since been written *around*
the leak: its worked example is ``instead p1 mills 2 cards``. **23 of 851
action rows carry a raw `p<N>`, and all 23 are this prompt; 0 other prompt
lines do** (#543).

Second finding from the same screen: with two Alchemists out the prompt has
**two rows that are the same answer**. `applicable_effects` pushes one
`Card` effect per *object*, while `Outcome::Replaced` is keyed by *card* —
the engine's own comment says "two Undead Alchemists mill once between them,
whichever is first". Playing seed 23 twice, answering row 1 and then row 2,
gives the same game: 20 differing log lines, all of them the name inside
`… (#3) applies first` vs `… (#4) applies first` (#545). N Alchemists is N
identical rows, by construction.

The other two surfaces were read at the same decision. The **CLI** shows the
same three rows under `─── Undead Alchemist (#3) would deal 4 combat damage
to you ───`, with `(you are p1)` in the header defining the token. The
**random seat** rolls: across 8 seeded games it chose the Flail 31 times and
an Alchemist 36 times, so this prompt is not one of H10's constants.

## H17 — the same schema, two providers

Method as H17 specifies: harvest every top-level shape, then check each
against what each backend's own code claims its provider enforces. Eight
distinct shapes over 851 requests, **0 illegal top-level keys** (#398's rule
still holds, and the harvest is still the only thing enforcing it in a
release build):

```
requests  top-level keys                                 features
     732  action,thoughts                                integer+enum
      73  attacker_indices,planeswalker_attacks,thoughts bare integer (source: "minimum": 0)
      25  mull,thoughts                                  boolean
       8  0,thoughts                                     integer+enum  (blocker assignment, enum [-1])
       4  0,1,thoughts                                   integer+enum
       4  order,thoughts                                 integer+enum  (array items)
       3  indices,thoughts                               integer+enum, minItems/maxItems
       2  dorks,floating,lands,rocks,thoughts            string+enum, empty properties {}
```

Two things worth keeping. First, **the harvest is post-sanitizer**: the
attackers shape arrives with `minimum` already stripped, so a stub harvest
shows what the CLI path sends, not what the caller built. Read the source for
the raw shape.

Second, the answer to H17's question. The comment at `llm.rs:3315` says
Anthropic rejects `minimum`/`maximum` and **Gemini rejects `enum` on integer
fields**. The first half is enforced — `sanitize_schema` strips them, and both
Anthropic-family backends plus both draft backends call a copy of it. The
second half is enforced nowhere: `GeminiBackend::send_with_schema` puts the
caller's schema into `"response_format"` verbatim, and so does the draft's
Gemini backend. **751 of 851 requests (88%) carry an integer `enum`** — every
menu choice, every blocker assignment, every ordering, every `mark_indices`
set. If the comment is right, a `gemini` seat 400s on all of them, and a 400
returns `{}` after one attempt (400 is not in the retry set), which is
index 0 — `Pass priority` — with six of ten callers logging nothing (#546).
The half this crew *can* test came back clean: one real
`claude -p --json-schema` call with the harvested blocker schema — top-level
properties literally named `"0"` and `"1"`, `"enum": [0,-1]` — was accepted
and answered correctly (`{"0": 0, "1": -1, …}`).

## H12 — the action label as a three-surface diff

The wrinkle H13 added is the sharp form: which `Action` variants have **no
arm** in `format_single_action` and fall through to `other => format!("{other}")`?

Six: `AbandonGame`, `BottomCards`, `DeclareAttackers`, `DeclareBlockers`,
`MulliganKeep`, `MulliganMull`. **None of them reaches a row** — 400 distinct
labels over 851 requests and not one `Display`-shaped label among them,
because each of those decisions has its own dedicated prompt (`mull`,
`card_indices`, the combat prompts) and never arrives through `choose_action`.
Both known drifts are **fixed and confirmed at runtime**: the mana row names
its colour (#460) and the loyalty row names the card, the cost, the effect and
the target — `Liliana of the Veil (#75) (your): -2: Target player sacrifices a
creature targeting Opponent` (#494), which is the row that was byte-identical
before.

The field diff that remains between the two tables is one entry and it is
dead: `format_single_action`'s `ActivateAbility` arm is a bare
`Activate <name>` with no tap plan and no targets, where the CLI's names both
— but no ability ever reaches it, because `choose_action` intercepts
`ActivateAbility` and builds the row from `legal.activatable_abilities`
instead (`Activate Inquisitor's Flail (Equip {2}) (tap 2x Island)`), and the
targets are a second question (`choose_ability_targets`) rather than a row per
target. That is a deliberate divergence from the CLI, which enumerates them,
and it is the right one for a menu that would otherwise be `|abilities| x
|targets|`.

One thing that *is* worth a look and became H18: the interception is
`if let Some(ab_idx) = legal.activatable_abilities.iter().position(…)`, and
when that lookup fails **nothing is pushed** — the legal action disappears
from the seat's menu rather than falling back to `format_single_action`.
Nothing tonight showed the two lists disagreeing; nothing checks that they
cannot.

## Found off-idea

- **Equipping to the creature it is already on logs `became unattached`**
  (#544). CR 701.3b: attaching to the object it is already attached to does
  nothing. `resolve_equip` calls `unattach` unconditionally, so the line that
  exists to tell a reader a bonus stopped applying (#502) fires when nothing
  changed. Reproduces on 8 of 10 seeds with committed decks
  (`wr-coverage` vs `bg-coverage`, `--p1 random --p2 random`), 2–13 times a
  game, on Inquisitor's Flail, Wooden Stake and Silver-Inlaid Dagger.
- **The ordering prompt's schema cannot express its own requirement** (#547).
  `choose_ordering` asks for a permutation in prose and emits an array with no
  `minItems`/`maxItems`/`uniqueItems`, so `[]` is schema-valid, is then
  refused client-side, and is replaced by the listed order with one
  `MALFORMED` line. `mark_indices` bounds itself for exactly this reason. Four
  occurrences tonight, all on damage assignment order — the prompt that
  decides which blocker dies.

## What held

- 0 invariant violations, 0 panics, 0 hangs across 43 games; every run exited 0.
- 0 illegal top-level schema keys in 851 requests, across 8 shapes.
- The CR 616.1 resolution itself is right: the chosen effect applies first,
  the doubling leaves a bigger event for the replacement, two Alchemists on
  one event mill once between them, and a second Zombie's unequipped damage

  `MALFORMED` at `Error` level and keeps a legal order (#399's rule holding).
