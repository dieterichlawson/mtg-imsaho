## V49 — the X you cannot buy

The idea predicted that `X (0-N)` promises values a `mana_per_tap > 1` group
makes unachievable, and that the four surfaces round down in four different
places. That is right, and there is a second, sharper defect underneath it
that the idea did not predict: **some of the values the prompt is blamed for
not being able to buy are values the board can pay exactly.**

### What is correct, and was worth checking first

The `{R}` pip is reserved before the funding options are built. With one
untapped Mountain and one untapped Sol Ring, casting Devil's Play offers:

```
─── Devil's Play (#43): choose X funding (0-2) ──────────────────
  Max X = 2
  Sol Ring x1 (2/tap, max 2)
  X (0-2, c = cancel the cast) =
```

The Mountain is not in the group list and `Max X` is 2, not 3 — so the
announce step does not spend the mana the rest of the cost needs. Checked,
correct. The group summary lines (`name xN (M/tap, max K)`) are also right
and are the only place the arithmetic is visible at all.

### #593 — the allocator misses exact allocations

`allocate_for_x` (`mtg-engine/src/funding.rs:191-206`) drains the pool, then
walks `options.groups` in category order (Lands → Rocks → Dorks) taking
`remaining / g.mana_per_tap` whole activations, and never revisits a group.
When a 1-per-tap group goes first and leaves a remainder smaller than a
later group's quantum, the later group contributes nothing.

Turn 6, two untapped Mountains and one untapped Sol Ring (one Mountain
reserved for `{R}`, so the offer is Mountain x1 + Sol Ring x1):

```
  Max X = 3
  Mountain x1 (1/tap, max 1)
  Sol Ring x1 (2/tap, max 2)
  X (0-3, c = cancel the cast) = 2
  (could not allocate final 1 mana due to source quanta; X = 1)
```

Board immediately after — the Sol Ring, which pays 2 by itself, is still up:

```
  Sol Ring
  Lands: 2x Mountain (tapped)
```

```
GAME	Funded X = 1
GAME	p0 cast Devil's Play (#46) (X=1) targeting p1
GAME	Devil's Play (#46) dealt 1 damage to p1 (19)
```

**X = 3 succeeds on the same board.** The larger X is buyable and the
smaller one is not, and the message names the wrong cause: it is not source
quanta, it is the order the allocator happens to spend in.

Worth preserving for whoever fixes it: the ordering *preference* — lands
before rocks before dorks, so a mana dork stays untapped — is deliberate and
good. It should survive as a tie-break among exact allocations, not be
dropped.

### #595 — the range is not a range, and the downgrade commits

With only a 2-per-tap source the achievable set is {0, 2}. Typing `1` is
accepted, funded at 0, and the cast completes:

```
  X (0-2, c = cancel the cast) = 1
  (could not allocate final 1 mana due to source quanta; X = 0)
```

```
GAME	Funded X = 0
GAME	p0 cast Devil's Play (#43) (X=0) targeting p1
GAME	Devil's Play (#43) dealt no damage to p1
```

The notice is on screen for 900ms and then the screen repaints with the card
gone. Every *other* rejection in this same reader loops and re-prompts —
`0x2` gets a second chance; a plain integer the program is about to not
honour does not. This is #123's shape one step along: no longer bare Enter
that burns the card, but a value the prompt itself offered.

### #594 — the page does the same thing and says nothing

`mtg-gui/src/prompts.ts:648-655` is a line-for-line JS copy of the same
loop, and the `if remaining > 0` arm that produces the terminal's notice was
never ported. `remaining` simply falls out of scope. Staged through
`window.mtgDebug.stage` against a real runner (the `mtg-gui/tests/widgets.js`
case-8 pattern):

| groups offered | `max_x` | typed | funded | `notice` |
|---|---|---|---|---|
| Sol Ring x1 (2/tap) | 2 | `1` | **0** | `null` |
| Mountain x1, Sol Ring x1 | 3 | `2` | **1** | `null` |
| Mountain x1, Sol Ring x1 | 3 | `3` | 3 | `null` |

The dialog before Enter reads `X (0-3)`, `MOUNTAIN X1 (1/TAP)`, `SOL RING X1
(2/TAP)` — the numbers that make the answer non-obvious — and then the
`Sol Ring` key is simply absent from the response it sends. The first row is
the worst: a card spent, the spell resolving for zero, and the page's only
record of it is that the opponent's life total did not move. Same shape as
#561 and #404 — a second copy of a path that missed the fix.

### The fourth surface is the control

`mtg-player/src/llm.rs:3589-3609` hands the model a per-group enum of legal
multiples and assembles `funding.taps` from what comes back, so a model can
answer `{"rocks":{"Sol Ring":"2"}}` and announce X = 2 exactly. **The one
seat with nobody at it is the only one that can buy the X the others are
told they can buy**, which is what settles this as an allocator defect and
not a rules limit.

`mtg-player/src/random.rs:126-127` rolls X across the whole range and then
calls the same allocator, discarding the shortfall:

```rust
let x = self.rng.gen_range(0..=options.max_announceable_x());
let (response, _shortfall) = mtg_engine::funding::allocate_for_x(options, x);
```

So on any board carrying a `mana_per_tap > 1` source the fuzzer announces an
X it did not roll, and nothing fires — `validate` is happy, because an
under-funded response is a legal one. That is the tail of #564: the roll was
added so intermediate X values would be exercised, and on exactly the boards
where allocation is interesting the rolled value is quietly replaced. Folded
into #593 as blast radius rather than filed separately, since it is the same
call.

## V48 — one number, four readers

The idea's premise is that the text-to-number readers are uniform inside
`cli.rs` (V46 established that) and stop being uniform the moment you leave
it. **For the two readers nobody had ever run, that is false**, and this
half of V48 can be retired.

### `--seed` and the deck-file count: uniform, and correctly refused

All twelve tokens plus `-1` and `2^64` through `--seed`, and thirteen deck
files through `load_deck_file`'s `COUNT NAME` reader:

| token | `--seed` | deck count |
|---|---|---|
| `+1` / `+20` | accepted | accepted |
| `007` | accepted | accepted |
| `-0`, `-1`, `0x2`, `0b11`, `2.0`, `1e1`, `1_0`, `""`, `" "`, `2abc`, fullwidth `４`, `2^64` | refused, token named, exit 1 | refused, `path:line: invalid count '<tok>'`, exit 1 |

Both are plain `str::parse`, so both agree with `cli.rs`'s nine to the
token, including the same `+3`/`007`-in, `-0`-out leniency V46 recorded. An
unknown flag exits 2, a fatal argument error exits 1; the refusal always
names the token it refused. Nothing to file.

Structural probes on the deck loader, also clean:

- `0 Mountain` loads and the game plays normally.
- an all-zero file (`0 Mountain\n0 Forest`) loses at turn 1 to CR 704.5b —
  rules-correct and explained, not a crash.
- `10000000 Mountain` aborts on allocation under `ulimit -v`. Not filed: an
  eight-digit count is not a shape a person meets, and the failure is not
  misleading, only large. Recorded so nobody re-derives it.
- `load_deck_file` splits on a single space, so a tab-separated file is
  refused with `expected 'COUNT CARD NAME'`. Two spaces are fine (the name
  is trimmed). Judged below the filing bar; noted here.

### #596 — `parse_int_str`, which the idea named and nobody had run

`llm.rs:3676-3679`:

```rust
let parse_int_str = |v: &serde_json::Value| -> u32 {
    v.as_str().and_then(|s| s.parse::<u32>().ok()).unwrap_or(0)
};
```

The X-funding schema is a per-group **string** enum, so `"0"`, `"2"`, `"4"`.
`as_str()` on a JSON number is `None`, so the same allocation typed as a
number reads as 0 for every group — and then `validate` **passes**, because
an empty response is a legal response, so `log_rejected` is never reached
and the rejection counter never moves.

Two stubbed `cc` games, same stub, same values, differing only in JSON value
type:

| run | funded X across the game | `invalid X funding` lines | `TOKEN_USAGE` rejections | outcome |
|---|---|---|---|---|
| numbers | `X funding sum = 0` × 11 | 0 | no clause at all | 130 calls, turn 69, decking |
| strings | 1, 8, 9, 9 | 0 | no clause at all | 35 calls, turn 18 |

What the operator sees in the failing run:

```
INFO	llm.rs:3708	CHOSE [P1]	X funding sum = 0
INFO	main.rs:107	GAME	Funded X = 0
INFO	main.rs:107	GAME	Devil's Play (#46) dealt no damage to p0
```

— byte-identical to a model that chose X = 0 on purpose. The counter works
(an earlier run of the same stub with malformed *action* answers reported
`34 answers rejected → fallback`); this path just never reaches it.

This is CLAUDE.md's rule 2 by a route the rule does not cover: the constant
is not chosen by the seat, it is manufactured by the parser. It also breaks
the pattern H14 recorded — every client-side validator now *substitutes*
rather than re-asks, which is right; substituting **silently and uncounted**
is what makes this one invisible.

Honest limit, also stated in the issue: a schema-compliant model returns
strings, so this needs a non-compliant response, and `structured_output` is
taken from the CLI verbatim with no schema check on our side. The reason it
is worth a number is the failure mode, not its frequency.

The counter-example done right is in the same repo:
`mtg-draft/src/deckbuilding.rs::card_count` refuses a count it cannot expand
rather than defaulting it, with tests naming that intent. The draft runner
has no X-funding path, so nothing needs porting there this time.
